## 1. Видение

- **Сеттинг:** стартап на полигоне **`coop_yard`**, общий спринт против «релизного» давления ИИ.
- **Четыре роли:** Admin → Developer → QA → PM (логический порядок периметр → код → качество → процесс).
- **Один бой / одна миссия** — общие метрики угрозы (THREAT / AI progress), баги, стресс, дедлайн; **разные инструменты** у ролей (типы карт). **Целевой кооп** — без жёсткого поочерёдного SDLC-фазирования; см. §4.
- **Общая цель боя:** команда выпускает **рабочее «приложение»** (условный релиз фичи) — один **общий прогресс релиза**. У каждой роли при этом **своя задача на игру**, которая **кормит** этот прогресс (разные рычаги, один счётчик/полоса успеха); см. §1c.
- **Два способа пати:** симуляция союзников (**`synthetic_bots`**) и **живая пати** (**`live_party`**) с серверным состоянием матча.

**Пиллары:**

| Пиллар | Смысл |
|--------|--------|
| Ролевая чистота | У каждой роли свой **каталог** карт; в конструкторе и справочнике не показывать чужие зоны. |
| Читаемый спринт | Игрок видит **свою ролевую задачу на бой** и то, как она **складывается в общий релиз**. |
| Общий провал/успех | Одна цель «приложение в прод»; провал/победа общие; роли тянут **разные рычаги** и могут **синергировать** картами (§2.5). |
| Сохраняемость | Роли, колоды, открытые карты, кооп-прогресс — совместимо с **sync** и сервером для live_party. |

## 1a. Состав команды и вход в бой (целевой процесс)

1. Игрок выбирает **одну из четырёх ролей**.
2. Оставшиеся **три** роли занимают либо **приглашённые люди** (группа / пати), либо **боты** (симуляция команды на одном клиенте — см. `synthetic_bots`).
3. Когда команда **заходит в бой**, все подключаются к **одному и тому же** спринту: **одна задача (ТЗ)**, **один оппонент**, **одна общая логика давления** (дедлайн, угроза, баги, инфраструктурные метрики — что уже моделируется общим состоянием / `shared` на сервере).
4. У каждого игрока **свой экран** и **своя колода** (своя «линия» карт и свои действия), но **каждое действие влияет на общий поток** боя: ресурсы, надёжность, баги на шине, стресс, прогресс по задаче.

---

## 1b. Роли в одном бою — кто за что отвечает (авторская формулировка)

| Роль | Функция в общем флоу |
|------|----------------------|
| **Admin** | Поддерживает **достаточный объём ресурсов** и их **надёжность**, чтобы разработчик мог выкладывать **пазл кода** (шина / CPU / RAM / mitigation в терминах игры). |
| **Developer** | Выкладывает **цепочку кода** по ТЗ на шине — основной носитель «фичи». |
| **QA** | **Отбивает** дефекты и вмешательства оппонента, которые **лезут к разработчику** (баги на шине, ICE, реакции на тип сбоя). |
| **PM (менеджер)** | **Усиливает команду**, помогает **снять стресс**, даёт **поддержку процессом** (SOFT: agile, daily, буферы и т.д.). При этом PM — **командное звено**: ему нужно принимать решения **вовремя**, опираясь не только на свою руку карт, но и на **состояние остальных**. |

Детальная модель «одна dev-задача → тест → инфра → руководство» и вклад в **общий релиз приложения** — §**1c**. Параллельно **тикает дедлайн** и **растёт стресс** (личный у каждого + агрегат команды — см. §2.4).

---

## 1c. Общая цель и **ролевая задача** на бой (авторская модель)

**Общая цель:** выпустить **рабочее «приложение»** — условный успешный релиз одной фичи/спринта; в UI это одна **общая полоса прогресса релиза** (или эквивалент: `projectProgress` + условия победы), на которую все роли работают параллельно.

**Поправка по ролям (одна связка на бой):**

| Роль | Задача на игру (что «закрыть» игроку) | Связь с общим прогрессом |
|------|----------------------------------------|---------------------------|
| **Developer** | Решить в бою **одну прикладную задачу** — собрать **цепочку кода / пазл ТЗ** на шине под выбранный стек. | Основной **двигатель** прогресса релиза: без доведения задачи до состояния «готово» релиз не клеится. |
| **QA** | **Протестировать** результат dev-задачи: снять дефекты, ICE, регресс, подтвердить качество в терминах игры (реакции / защита на шине). | Защищает прогресс от отката ИИ; успешные проверки и снятие рисков **добавляют** в общий релиз / снимают «красные» флаги. |
| **Admin** | **Создать и удержать инфру** под эту же связку: ресурсы, надёжность, контур, чтобы код и проверки вообще были возможны. | Поднимает потолок действий dev/QA (CPU/RAM/mitigation и т.д.) и **стабилизирует** общий прогресс против инфра-ударов оппонента. |
| **PM** | **Руководить и поддерживать**: стресс, дедлайн, процесс (SOFT), синхронизация команды (в т.ч. чекпоинт стейта — §4.2). | Ускоряет или спасает чужие ролевые задачи; баффы и снятие стресса **переводят** командные метрики в прирост общего релиза. |

Итого: не «четыре отдельных мини-игры без связи», а **одна поставка** с четырьмя **понятными вкладами**, каждый из которых игрок видит у себя на экране как **свою** задачу и как **долю в общем**.

## 2. Роли — как **должно ощущаться** (целевой UX)

Согласовано с `COOP_ROLE_LABELS`, `COOP_MISSIONS_AND_AI`, плейтест-отчётом и запросами на доработку UX.

### 2.1 Developer

- **Ролевая задача на бой:** одна **фича / ТЗ** — довести **цепочку кода** на шине до состояния «задача решена» (синтаксис / функции / стек).
- **Фантазия:** основной носитель **цепочки ТЗ** на шине (синтаксис / функции / стек).
- **Давление ИИ:** ревью, темп, угроза растёт, если код не двигается.
- **Дек:** языковое ядро + выбранный **стек** (Java / Kotlin / Python / Go); без чужих категорий.
- **Статус в переписке:** относительно остальных ролей — «ещё кое как играбельно» (**эталон** для остальных).

### 2.2 QA

- **Ролевая задача на бой:** **протестировать** то, что собрал dev — закрыть дефекты и риски по этой же задаче (шина, ICE, типы сбоев).
- **Фантазия:** **REACTION / DEFENSIVE**, outplay по `problemType`, снятие ICE/багов с шины, регресс и «периметр качества».
- **Давление ИИ:** дефекты, ICE, плотность событий (в т.ч. вокруг «окна проверки» dev-задачи).
- **Синергии (цель дизайна):** пары карт в **одном ходу** дают усиление (см. `coopCombatRole`, отчёт плейтеста: trace→spoof, log_mask→firewall и т.д.); возможны **кросс-синергии** с порядком ходов dev/QA (TBD в балансе).
- **Параллельное окно / live_party:** действия вроде **`apply_qa_defense`** — вклад в общий `bugPressure` / защиту.
- **Запросы из переписки:** не ощущаться «сломано» относительно dev; темп хода — **шире рука/дро** для комбо поддержки (`coopSupportComboTempo`).

### 2.3 Admin

- **Ролевая задача на бой:** **поднять и удержать инфру** под текущую dev-задачу и проверки QA (ресурсы, надёжность, контур).
- **Фантазия:** **INFRA + SCRIPT** как проводка к периметру; **ресурсы и надёжность контура** (слоты / mitigation / LB / серты / кластеры), чтобы dev мог выкладывать код.
- **Параллель / live_party:** **`apply_admin_infra`** и т.п.
- **Запросы из переписки:** не чувствовать себя обойдённым по сравнению с dev; ясный **пайплайн** (логи `[ADMIN:PIPE]`).
- **Реализация сейчас (legacy):** в коде кооп всё ещё опирается на фазу **ARCHITECTURE** только для админа — это **не** целевая модель; см. §4.

### 2.4 PM — командное звено (расширенная цель)

- **Ролевая задача на бой:** **руководство и поддержка** — удержать команду в состоянии, когда dev может добить задачу, QA — проверить, admin — не потерять контур; плюс синхронизация стейта (§4.2).

**Роль в команде:** менеджер не только «играет в SOFT ради себя», а **связывает команду**: по таймингу накладывает баффы, снимает стресс, держит дедлайн — в момент, когда это **нужно** dev / QA / admin.

**Колода и линия противодействия:** своя рука карт против **стресса** и бизнес-рисков оппонента; карты процесса (**AGILE**, **DAILY**, ритуалы, буферы, фокус**) — как усилители союзников и стабилизаторы темпа.

**Метрики стресса (двухуровневые):**

- У **каждого** члена команды есть **личный стресс** (то, что давит на роль в её контексте).
- Есть **общий стресс команды**: агрегат, **складывающийся** из стресса игроков (или согласованная формула поверх личных — зафиксировать при реализации: сумма / среднее с потолком / взвешенная).

**Видимость «прогресса по задаче»:** PM (и по желанию дизайна — частично другие роли) видит **прогресс по задаче** (единый спринт / ТЗ), чтобы **вовремя** играть карты поддержки, а не вслепую.

**Панель «общий план проекта» (небольшая, постоянная):**

- Компактный **план спринта / доска угроз**, на которой видно, **какие проблемы оппонент выкладывает** в зону **QA**, **Admin**, **PM** (и при необходимости — критичные сигналы для dev), чтобы менеджер **оркестрировал** ответ командой.
- Рядом или внутри той же зоны — **условные мини-графики** (или sparkline / шкалы) **состояний остальных игроков**: стресс, ключевые параметры роли (например, заполненность инфры у админа, плотность багов у QA, полоса прогресса dev), чтобы визуально читать «кому сейчас плохо».

**Связь с текущей реализацией:** частично пересекается с `CoopTeamSitrep`, подсказками оппонента и `netMatch.shared` в live_party; **полноценные** личные стрессы по ролям + общий агрегат + отдельная панель плана с разбивкой угроз по ролям — **целевой UX, к реализации** (см. §10).

**Техническое (уже в коде):** цепочку кода на шине в synthetic yard для PM по-прежнему ведёт **синтетический DEV** (PM не кликает по кодовым слотам); **PROJECT%** не должен залипать на 0 из-за пустой локальной шины (`useCombatLogic` + `shared.projectProgress` в live_party). Параллель / сервер: **`apply_pm_support`**, **`release_check`**, linked objectives — `coopLinkedRoleObjectives.ts`.

### 2.5 Синергии карт и командные комбо

- **Внутри роли:** последовательности карт в одном ходу или в соседних ходах дают бонусы (уже заложено в `coopCombatRole.ts`: QA trace→spoof, admin ping→ssh, PM coffee→focus и т.д.; см. `design/COOP_PLAYTHROUGH_REPORT.md`).
- **Между ролями (цель):** успех или провал **одного** открывает окно для **другого** (например, dev закрыл цепочку → QA получает бонус к проверке; admin поднял надёжность → dev дешевле кладёт следующий слот; PM сыграл daily → снял стресс QA перед тяжёлой реакцией). Конкретные правила — таблица баланса + серверные флаги в `shared` / события матча.
- **Связь с linked objectives:** подзадачи не-dev (`coopLinkedRoleObjectives.ts`) — ранний вариант «ролевой задачи на бой»; при расширении модели §1c их можно **выровнять** с явными целями «протестировать / поднять инфру / поддержать релиз».

## 4. Цикл боя и миссии (целевой дизайн vs код)

### 4.1 Полигон и мета (без изменений по смыслу)

- Миссии **`coop_yard_*`**, тиры junior → mid → …; онбординг **10** junior, далее пул **Codewars**; босс после порога — см. `COOP_MISSIONS_AND_AI.md`.

### 4.2 Целевой кооп-бой: **без фазирования SDLC**

**Замысел автора:** жёсткое **фазирование** вида ARCHITECTURE → DEVELOPMENT → VERIFICATION → DEPLOYMENT **не требуется** для кооп-спринта. Вместо этого:

- **Один непрерывный (или слабо сегментированный) бой** на общую задачу: дедлайн тикает, **активный ИИ-оппонент** каждый ход (или тик) **реально бьёт по команде** — выбор действий, давление на метрики, целенаправленные удары по ролям, а не «фоновая декорация».
- **Прямое влияние классов (ролей):** удачные и неудачные действия **одного игрока сразу отражаются** на общем состоянии и на **других** (стресс, баги, ресурсы, прогресс задачи, доступность действий). Нет ощущения «я в своей фазе, остальные не в игре».
- **Единый стейт матча** (на сервере в live_party, авторитетный снапшот), с которого **все экраны** читают одни и те же числа и события.
- **PM как точка синхронизации:** у менеджера есть возможность **зафиксировать / сохранить состояние** (условный **чекпоинт синхронизации**): после него все клиенты выравниваются на один и тот же снапшот — чтобы убрать рассинхрон и дать команде общую «правду» перед следующим витком давления ИИ.

Итого: кооп — это **общий поток против ИИ** + **кросс-ролевые эффекты** + **синхронизация экранов** (в т.ч. через действие PM), а не гейт «NEXT пока не закроешь фазу».

### 4.3 Что в коде сейчас (расхождение с §4.2)

Клиентский бой всё ещё построен на **`SDLC_PHASES`** и `currentPhase` (`useCombatLogic`, `CombatPhases`): ARCHITECTURE / DEVELOPMENT / VERIFICATION / DEPLOYMENT, с особыми правилами для кооп-ролей (пропуск архитектуры, рука стабилизации, `canAdvancePhase`). Это **наследие**, которое нужно **постепенно заменить** или сильно упростить под модель §4.2, не ломая соло-квесты без отдельного флага `sessionMode === 'coop'`.

### 4.4 ТЗ на шине и прогресс (до миграции фаз)

- **Execution chain:** пошаговое ТЗ на шине; в synthetic yard префилл цепочки ботом-DEV для не-PM; PM — без визуала кода на шине, но с корректным **PROJECT%** (§2.4). После перехода к §4.2 — пересмотреть, как «пазл кода» и общий прогресс ведутся без фазовых кнопок.

### 4.5 Связанные цели не-dev

- Масштаб порогов от длины ТЗ (`buildCoopLinkedRoleObjectives`); награда в **playerProgress**; **flush на сервер** (`apply_linked_sprint_progress`) — совместимо с общим стейтом; при снятии фаз — привязать награды к **событиям матча**, а не к `advancePhase`.

- **Документация кооп-каталога:** один экран без лишней вложенности **полноэкранной** раскладки внутри `neon-panel` (исправлено: отдельный стек «интро + каталог»).
- **Боевой HUD:** для live_party — метрики с **`netMatch.shared`**; чеклист реализации dev может скрываться у не-dev (`hideDevImplementationChecklist`).

- **PM (цель):** панель команды: **личный + командный стресс**, **прогресс задачи**, **план угроз по ролям**, мини-индикаторы союзников (см. §2.4).

## 7. Запросы автора из переписки (для приоритизации)

Формулировки обобщены (не дословные цитаты):

1. Связать **цели не-dev** с объёмом dev-миссии и **playerProgress**; для **live_party** — **серверный** учёт наград linked objectives.
2. Устранить **краши** боя при расхождении RAM-слотов и длины рельсы (`runtimeRail` vs `ramSlotsMax`).
3. **PM:** не «всё уже построено» на шине, но и не «я не понимаю, что делать» / не залипание фаз из-за **0% PROJECT**.
4. **Документация:** не «скукурузило» от вложенных контейнеров при входе в карту каталога.
5. Общее: **не-dev должны ощущаться не хуже dev** по ясности петли и честности метрик.
6. **Пост-бой:** после победы / поражения — **отчёт с оценками игры** по роли (вклад в метрики, тайминг поддержки, ошибки); детализация шкал — TBD.
7. **Кооп без SDLC-фаз:** общий стейт, кросс-ролевые последствия ходов, **PM-сейв стейта** для синхронизации экранов, **активный** ИИ против всей команды (§4.2).
8. **Ролевая задача → общий релиз:** dev одна задача в бою, QA тестирует её, admin — инфра под всё это, PM — руководит и поддерживает; плюс **синергии** карт (§1c, §2.5).

## 10. Открытые вопросы и разрыв с реализацией

- **Ролевые задачи в UI:** отдельные чеклисты / один экран «вклад в релиз» для каждой роли; как визуально связать §1c с одной полосой `projectProgress`.
- **Кросс-ролевые синергии (§2.5):** какие пары ролей+карт кодировать первыми; анти-эксплойт (не усиливать AFK).
- **Миграция с фаз на общий поток (§4.2–4.3):** отдельный техдизайн: что остаётся только в solo, что выключается в `coop_yard` / live_party; как заменить `advancePhase` на тики дедлайна / волны ИИ.
- **Чекпоинт PM:** семантика (раз в N ходов, после критического события, цена в CPU/карте); API матча (`release_check` vs новый `sync_checkpoint`); права только PM или и лида.
- **PM-панель:** реализовать **агрегат стресса** + **персонифицированные стрессы** ролей на клиенте (для bots — синтетические значения или производные от общего состояния); для live_party — поля в `shared` / события матча.
- **Графики:** уточнить тип (sparkline за N ходов, столбцы по фазам, только «сейчас»); ограничение по месту на экране мобильного/десктоп.
- **«План проекта» с угрозами по ролям:** как маппить существующие `BugAction` / `NEXT_INTENT` на «колонки» QA / Admin / PM / Dev без дублирования шума.
- Нужен ли **отдельный** «учебник первого спринта» на экране для QA/Admin/PM (не только лог)?
- Для **live_party QA/Admin**: достаточно ли текущей синхронизации шины/прогресса или нужен отдельный UX «смотри shared, а не только локальную шину»?
- **Пост-отчёт:** какие именно **оценки** (S/A/B, процентили, комментарии ИИ); нужен ли общий экран команды или только личный.
- Тон и **сложность** ИИ по ролям — финальные коэффициенты (`coopAdjustAiDeltas`) зафиксировать playtest-таблицей.
