## 1. Нелинейность у джуна (elif, несколько веток)

Сейчас `isExecutionChain` в бою — по сути **одна линия** слотов: хорошо для «скелета сверху вниз», плохо для **альтернативных путей** без дублирования карт.

**Варианты обыгровки (можно комбинировать):**

1. **Несколько микро-миссий вместо одной**  
   - Миссия A: только guard (пустой список → 0).  
   - Миссия B: happy-path (foreach / stream → sum).  
   Обе дают прогресс «эпика», игрок не жмёт if и for в одну линию.

2. **Группы шагов с OR внутри группы** (расширение модели ТЗ)  
   - Шаг «BRANCH_HEAD» принимает `syntax_if` **или** карту «метки ветки» (новая механика).  
   - Дальше две **подцепочки** как отдельные списки шагов `branchA[]`, `branchB[]` — в UI две короткие рельсы или вкладки.  
   Требует доработки `TechnicalTask` и UI, зато ближе к реальному коду.

3. **«Достаточно покрыть множество» без порядка** (`isExecutionChain: false`)  
   - Шаги остаются, но прогресс = доля выполненных **без** строгого индекса.  
   - Минус: слабее ощущение «компиляции по строкам».

4. **Else-if как последовательность guard’ов**  
   - Каждый elif — отдельный шаг «IF + специфичная карта реакции на тип ошибки»; ветка «иначе» — следующий шаг.  
   - Визуально линейно, логически — цепочка предикатов, как в реальном `if / else if`.

5. **PM / QA как носители ветки**  
   - Например, «пустой список» закрывается не второй веткой кода, а **обязательным** тест-кейсом QA (карта + текст), а дев пишет только happy-path.  
   Уже частично описано в плейбуке BANK-JU-001.

**Сомнение:** без изменения модели ТЗ самый дешёвый путь — **(1) + (5)**; полноценный DAG веток — отдельный крупный фича-коммит.

## 2. Админ: панель заполняемости шины vs подсказка в ТЗ

**Идея A — доп. панель у админа**  
- Видит **сколько слотов шины занято / лимит** (`ramSlotsMax`), сколько шагов у текущей миссии девелопера, прогресс % по ТЗ.  
- Плюс: админ действует «по ситуации», меньше метагейма в чате.  
- Минус: нужен UI + источник истины (общий стейт миссии в коопе).

**Идея B — блок в ТЗ админа (или общей миссии)**  
- Явные строки: «целевой RAM ≥ …», «целевой CPU ≥ …», «слотов шины ≥ N» (формулы как в `java_junior_card_playbooks.md`).  
- Плюс: дешевле в реализации, хорошо для обучения.  
- Минус: при смене баланса формул нужно обновлять тексты.

**Идея C — гибрид**  
- В ТЗ базовые числа для «типовой» миссии недели + панель показывает **факт** и **дефицит** (красным), если факт ниже цели.

**Рекомендация на ближайший этап:** сделать **B** в данных миссии / брифинге босса полигона, затем **A** как QoL, когда появится стабильный общий стейт «шина девелопера» для админа в бою.
